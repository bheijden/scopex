before you trust any of it Seven parsers in this package have shipped broken, each returning a plausible empty or wrong answer rather than an error — including one that named the wrong pass on four cases. Run scopex.selftest() and scopex.conformance() in a fresh process after any jax upgrade. They fail loudly.

How do I use this?

The documentation. The differential method, profiling any program versus instrumenting your own framework, the naming contract, the accessors that silently return nothing, the API, and a runnable recipe per question.

blueprint →

Can I trust this number?

Per instrument: what validates it, where that validation fails, what it cannot see, what it costs. A wrong method is worse than a missing one, so the blind spots are written down rather than discovered.

deficits →

Show me how, on a real case.

20 runnable files, one per question — which pass grew the module, who is slow inside tracing, where did the seconds go when the passes explain none of them. Each names the pathology it was written against and the numbers it was derived from.

recipes →

Did this ever work on a real problem?

The evidence behind the recipes: the same 28 compiles, indexed by where the cost lived rather than by question. What each instrument showed, what it missed, and where the trail left scopex for XLA source. Read it to decide whether to believe a claim.

investigations →

I am changing a parser, or I just upgraded jax.

Every place scopex reads text a compiler printed, what produces that text, what happens when the producer changes it, and how the two self-checks cover each one.

hardening →

What is it tested against?

62 case files, 800 entries — each a real pathology with a fast control and a declared platform, because a slow compile with no fast twin is just a big program.
