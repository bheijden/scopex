scopex

Flags

Every XLA flag and JAX config option this project set and observed, with what it measured and what it costs. Most of them are nulls — that is the finding, and it is why the list is worth having: it is a list of things you do not need to try.

Measured on jax / jaxlib 0.10.2, jax[cuda13], sm_89, CUDA 13.0, 20 cores. 309 of 416 probed --xla_* names parse in this build.
Read the four traps first — three of them fail silently, which is worse than failing. Then §A, which is the highest-leverage group here by a wide margin.
Before you set anything: a flag is not a lever until you know your regime The same flag measured 41× on one program and 1.00× on another. Classify first with scopex.regime(scopex.record(fn, *args)), and confirm with scopex.custom_calls(compiled) — a zero count of gemm_fusion_dot / triton_softmax makes the matching flag a provable no-op, confirmed by a byte-identical optimized module. Presence is necessary, not sufficient.

And XLA_FLAGS is read once, when the backend is constructed. Setting it after your first compile is a silent no-op — scopex.dump() and scopex.backend_initialized() both raise rather than let that happen quietly.

309 of 416 probed --xla_* names parse in this build. Every entry below was either set and observed, or its absence was confirmed by the flag parser aborting. Read the four traps first — three of them fail silently, which is worse than failing.

The four traps on pass-disabling flags

Trap 1 — an unknown PASS NAME is silently ignored, and the log echoes your typo
you writeresult
this-pass-does-not-existrc 0, module byte-identical (163 instr / 21537 bytes), 189 passes still ran

The VLOG line Passes disabled by --xla_disable_hlo_passes: X echoes whatever you typed, existing or not. It is not confirmation. The only real confirmations are (a) the pass name vanishing from the HLO pass: <name> time: lines, (b) a moved structural panel with autotune_level=0 pinned, or (c) an Out of fuel for line.

The asymmetry that will save you: an unknown --xla_* flag is FATAL — F… parse_flags_from_env.cc:234] Unknown flag in XLA_FLAGS. An unknown pass name inside a valid flag is silent. So --xla_disable_hlo_passes=<garbage> always "works". This bites both directions: instruction_fusion and fusion_merger both parse cleanly and neither pass exists. measured here
Trap 2 — a PIPELINE name matches too, and only TOP-LEVEL ones tell you GetEnabledPasses first checks the pipeline's own name and returns {}.
· =fusion (a top-level pipeline) prints Disable the full pass: fusion, kills priority-fusion and multi_output_fusion, takes a synthetic module 163 → 402 instructions and 15 → 107 computations, and compiles 1.79× SLOWER.
· =simplification (a nested pipeline) prints NO confirmation line at all, because the parent's filter removes it and the sub-pipeline is never entered — while still changing the module (189 → 178 distinct passes). You get zero feedback for the nested case.

The one that will actually break your program: post-scheduling-passes → remat-pipeline contains rematerialization + stream-attribute-annotator + cse_barrier_expander, which is OptimizationBarrierExpander. So --xla_disable_hlo_passes=remat-pipeline gives JaxRuntimeError: INTERNAL: Unsupported instruction opcode: opt-barrier on any program using lax.optimization_barrier — and one real program's entry module carried 168 of them. Disable the child pass rematerialization by name; that is rc 0 with a byte-identical module and is your NULL ARM. measured here
Trap 3 — both flags together ABORT; and disable_all does not work on GPU --xla_disable_hlo_passes + --xla_enable_hlo_passes_only together trip CHECK(disabled.empty() || enabled.empty()): rc −6 (SIGABRT), F… hlo_pass_pipeline.cc:254. Both echo lines print first, so a log showing both is a log of a process that died.

--xla_disable_all_hlo_passes=true takes precedence and short-circuits before that CHECK (so combining them gives rc 1, not −6) — and it fails with INTERNAL: Unsupported instruction opcode: iota inside apply_primitive, i.e. on an eager op before your jit ever runs. Some passes are legalization, not optimization. --xla_enable_hlo_passes_only is unusable for the same reason: =dce → 1 pass → iota failure; =simplification → a pipeline name clears the filter and enables everything inside it (20 passes) → still fails. Corroborated upstream by openxla/xla #12850, closed with no answer. measured here
Trap 4 — a strings hit in the binary does NOT prove a flag exists --xla_gpu_enable_dot_strength_reduction, --xla_gpu_simplify_gathers and --xla_gpu_simplify_scatters all appear in the plugin's string table and all three die with Unknown flag in XLA_FLAGS — they are reserved names in xla.proto, and reserved names are still compiled in. Always set the flag in a subprocess and see whether XLA dies. this bit us — a prior campaign used all three as measurement arms; those arms aborted the process rather than producing null results

And XLA_FLAGS=--help is not the flag list: tsl prints the whole usage inside one absl LOG(FATAL), which truncates at 15,000 bytes — the dump stops mid-word after 78 of the 309 flags that exist. Enumerate with strings -n 8 <plugin>.so, then confirm each one parses.

A · Persistent cache — the highest-leverage group in this document

knobdefaultwhat it does · effect · caution
jax_compilation_cache_dirNoneThe master switch; nothing else turns the persistent cache on. Warm hits measured on three f64 solvers: 8.56 → 4.81–5.11 s wall, 30.08 → 13.76–14.13, and 30.81 → 11.17–12.62. It also silently enables the per-fusion autotune cache (below) and bakes its own absolute path into every cache key.
jax_persistent_cache_min_compile_time_secs1.0Set this to 0. The largest measured saving in the project: 0.51× of per-edit compile on a 10k-instruction solver (36.45 → 18.68 s; 0 hits → 347 hits / 17 misses) and 5.5× on a smaller program's second run. At the default, every sub-second module — i.e. the entire eager-construction tail — is never written and is re-paid on every process start, forever. The trap is self-concealing: the cache directory still fills with xla_gpu_per_fusion_autotune_cache_dir/*.textproto, so ls says it works. Check the cache_misses event (which counts writes) instead. Not an XLA_FLAGS value, so not a cache-key input.
jax_persistent_cache_enable_xla_caches'xla_gpu_per_fusion_autotune_cache_dir'Default already gives you the per-fusion autotune cache — 0.08× on an edit recompile of an autotune-bound MLP. 'all' adds xla_gpu_kernel_cache_file and force-sets xla_gpu_enable_llvm_module_compilation_parallelism=True; measured, the kernel cache gives ~4% kernel reuse on the friendliest possible edit and +7% cold. 'none' is what makes the cache portable across directory paths (§1.5). Changing this value at all invalidates every existing entry.
jax_compilation_cache_max_size-1Leave it. Any other value needs filelock (not installed here) and, without it, kills the cache for the whole process with one UserWarning per read: 0 hits / 0 misses / 0 entries on both runs, against 3 misses / 4 entries then 3 hits without. max_size=0 does not "disable caching" as its help text claims — it hits the filelock error first.
jax_persistent_cache_min_entry_size_bytes0Documentation-only in this OSS build: default_min_cache_entry_size() returns 0, so the documented "override" never fires and 0 behaves as −1.
jax_compilation_cache_include_metadata_in_keyFalseLeave False. True skips the strip-debuginfo pass, so file names and line numbers enter the key and the entire 18-item free-edit list turns off — a bare comment becomes a full recompile.
jax_compilation_cache_check_contentsFalseDebug only. VerificationCache.get returns None the first time a key is seen in a process, forcing a recompile, then compares against disk. Warm run: 0 hits, 2 re-writes — it destroys the cache benefit by construction. Its CacheVerificationError is re-raised regardless of raise_persistent_cache_errors.
jax_raise_persistent_cache_errorsFalseGenuinely useful in CI: turns the silent-cache-death mode into a crash. Without it a broken cache costs you every compile and prints one warning you will not read.
jax_enable_compilation_cacheTrueMaster off switch; emits task_disabled_cache. Use JAX_ENABLE_COMPILATION_CACHE=false in any timing harness, or assert not jax.config.jax_compilation_cache_dir.
host callbacks—Not a knob — a landmine. A single jax.debug.print, io_callback or breakpoint() anywhere in the module means the entry is never written (compiler.py:809-813), forever, silently. Undocumented on the official persistent-cache page, which lists only the custom_partitioning caveat.

jax_check_tracer_leaksFalseMoves an UnexpectedTracerError to the leak site. "Some caching is disabled" per its own help — a debugging tool, never a benchmark setting. Not in trace_context(), so it does not itself retrace.

D · API-level knobs

knobeffect · caution
static_argnums / static_argnames2,872× in seconds for 5 distinct static values vs 5 identical, on a 60-op chain. Static args are boxed in _HashableWithStrictTypeEquality, whose __eq__ is type(a) is type(b) and a == b — so 1 ≠ 1.0 despite 1 == 1.0 and hash(1) == hash(1.0), 1 ≠ True, 2.0 ≠ np.float64(2.0). Each mismatch is 2 traces. Normalise numeric statics at the boundary (int(k)), and give any config/dataclass passed as a static arg value-based __eq__/__hash__ — 3 freshly-constructed configs with default identity hashing gave 3 traces; with value hashing, 1. An unhashable static arg raises rather than silently missing.
jax.jit(..., compiler_options={...})
Lowered.compile(compiler_options={...})		The recommended transport for XLA options. In-process, per-jit, no restart, no XLA_FLAGS. Typos and type errors are loud here (INVALID_ARGUMENT: No such compile option; 'not_an_int' is not a valid int32 value) where XLA_FLAGS gives a bare parse failure. Lets you A/B two settings in one process — verified autotune_level=0 taking a 6.614 s compile to 0.530 s in the same process. Two gotchas: lowercase "true" is REJECTED (pass a Python bool, "True", or 1); and a bad pass name inside xla_disable_hlo_passes is still silent. Four keys are intercepted by JAX and set on build_options directly: exec_time_optimization_effort, memory_fitting_effort, optimization_level, memory_fitting_level. It is hashed into the persistent-cache key.
jax.export.export / Exported.call13.98× / 14.57× / 18.35× on trace+lower with byte-identical post-opt HLO and bit-identical outputs. See §1.4. Does not touch XLA compile; produces a second cache entry; costs one full trace to build.
jax.jit(f).trace(*a) → TracedThe cheap inspection point: .jaxpr .in_avals .out_avals .in_tree .out_tree .args_info .out_info .fun_name .donate_argnums .lojax .lower(). in_avals, in_tree and donate_argnums come from the Stage base and are not on the AOT doc page. Traced.lower(lowering_platforms=('cpu',)) lowers for a platform you are not on — the supported way to compare backends without a second machine.
jax.eval_shapeNOT a cheap shape-inference shortcut — in 0.10.2 it is literally jit(fun).trace(*args).out_info, measured 169.2 ms against 188.9 for a full .trace() on the same cold program. It is useful: it shares the tracing cache (so it pre-warms), and it returns in 6.4 ms on a (1e5,1e5) f64 matmul with no device memory. An unhashable fun is silently wrapped in functools.partial — a new object every call, so it can never hit the cache (3 calls → 3 traces).
lax.scan(..., unroll=k)Free at trace time (recursive equations constant at 6 for unroll 1→256); 2.08× on lowering at unroll=256. Safe up to k≈16 (~0.02 ms/iteration against 89 ms for a full unroll). Compile-stage effect not measured.
lax.optimization_barrierA real fusion boundary (its opcode is off IsFusible's allowlist), surviving grad, jvp, vmap and grad² with bit-identical outputs. GPU-specific as a compile lever, ~5.7 ms per barrier, and see §7 for how badly it fails to transfer. Counting it via compiled.as_text().count('opt-barrier(') always returns 0 — OptimizationBarrierExpander erases them post-scheduling. Count in lowered.compiler_ir('hlo').as_hlo_text().
jf.clear_cache() / jax.clear_caches()Required for honest cold-trace benchmarking. jax.clear_caches() clears 110 registered caches process-wide. Caution: it also drops xla_primitive_callable's cache, so any eager op in your benchmark re-compiles its one-op module every round — that inflated one arm by 1.26× until isolated. Neither touches the persistent cache.
jax.named_call / jax.named_scopeINERT in 0.10.2. 7 scopes added to a real program left the jaxpr at exactly 7,658 equations, a byte-identical primitive dict, before-opt HLO at exactly 9,412 lines, and a byte-identical cache key. named_call is documented here as "a version of fun wrapped in a named_scope". Advice to avoid it as a fusion barrier is stale. It also does not appear in a profiler trace (0 hits / 34,403 events) — it is HLO metadata only; use jax.profiler.TraceAnnotation.
jax.InlineDoes not exist here. Landed in jax 0.11.0 (2026-07-16). jax.jit already takes inline: bool; 0.11.0 turns that into a policy enum. The one forward-looking knob plausibly aimed at the unrolled-chain problem — worth re-testing after a version bump.

--xla_dump_hlo_pass_re semantics — the web gets the boolean backwards The dump condition is !dump_regex.empty() && (pass_changed || dump_regex != ".*"). Read it carefully:
· ".*" → (pass_changed || false) → dumps only where the pass reported changed.
· any narrow regex → (pass_changed || true) → dumps UNCONDITIONALLY.

Proof: pointing a narrow regex at triton-softmax-rewriter — a pass previously proved to be a byte-identical no-op on that program — still produced exactly 2 snapshot files per compile. DeepWiki states the opposite. Also: the regex is tested against both before_pass_name and after_pass_name, which is why one narrow name yields a matched before/after pair. And "changed" is the pass's returned bool, not an instruction-count diff — under .* you will see rows with Δinstr = 0 (sanitize-constant-names renames without adding anything). A snapshot existing does not mean the pass grew the graph. measured here

H · CUDA environment — every one is a null, and that is the finding

Nine arms × 2 reps × 4 usable rounds on a 10k-instruction f64 solver. The NULL arm came out top of the table at 1.092×, and a second null pair agreed to 0.999× — so the whole group spans 0.962–1.092 and the noise is the largest effect in it. Nothing here is a compile knob. Three entries still matter, for reasons other than speed:

  • CUDA_LAUNCH_BLOCKING=1 is runtime poison, not a compile knob. Compile untouched; first launch ×2.12 and warm launch ×2.40. The asymmetry makes it easy to misread as "compile got faster". assert not os.environ.get("CUDA_LAUNCH_BLOCKING").
  • CUDA_CACHE_* does nothing — 0 files written in every arm and rep, because the driver JIT cache is not on XLA's path at all (§1.10). A warp-lang positive control in the same setup wrote 3 files, so this is a real negative.
  • ptxas 12.8 vs the wheel's 13.3 is a silent-swap hazard, not a speed knob — 1.020× end to end, and offline on 40 kernels the SASS instruction counts are IDENTICAL in 40/40.

CUDA_VISIBLE_DEVICES deserves its own line, because the failure mode is silent: "" or a nonexistent index gives rc 0, no warning, and jax.devices() quietly becomes [CpuDevice(id=0)]. Your "GPU compile benchmark" just became a CPU compile benchmark on a different pass pipeline with no ptxas at all. It also renumbers, so any pinning downstream mismatches nvidia-smi's physical indices.

CUDA_ROOT is read by jax._src.lib._cuda_path() first and becomes xla_gpu_cuda_data_dir — i.e. it decides which ptxas binary compiles your kernels. Point it at an empty directory and XLA silently falls through to /usr/local/cuda/bin/ptxas. Always print the assemble_compilation_provider.cc:227 line when reporting a compile number. Dumped PTX is version-locked: XLA emits .version 9.0 and ptxas 12.8 rejects it outright, so any offline ptxas study must use the wheel's binary.

I · CPU-backend flags — nothing wins, and here is the null that proves it

A 4.7k-instruction f64 solver on CPU, 3 rounds, arm order rotated, median of per-round ratios. The critical control: --xla_gpu_autotune_level=0 on the CPU backend cannot possibly change a CPU compile, and it measured 1.149×. That is the noise floor of the protocol, and eight of the nine arms sit inside it — including --xla_cpu_opt_preset=FAST_COMPILE at 1.107 despite its name, and despite demonstrably taking (8885→8770 instructions).

The one arm below the floor is --xla_backend_optimization_level=0 at 0.854 — and it costs 1.35–2.81× WARM. On CPU this flag maps to LLVM CodeGenOptLevel and is the only knob that moves anything at all; on GPU it is inert. Everything else measured null: llvm_disable_expensive_passes, cpu_parallel_codegen_split_count at 1 and 128 (splitting is at LLVM-function granularity, so one huge kernel is indivisible regardless of N), cpu_use_xnnpack=false, and both xla_backend_extra_options LLVM toggles.

Six xla_cpu_* names in the binary are NOT flags and abort the process if passed via XLA_FLAGS: disable_loop_unrolling, disable_slp_vectorizer, disable_tiled_emitter, disable_new_fusion_emitters, flatten_after_fusion, use_multi_output_fusion. They are keys of the xla_backend_extra_options map — pass them that way. And --xla_cpu_use_thunk_runtime warns "no longer supported": any advice telling you to toggle it is out of date.

J · Flags that do not exist in this build

107 of 416 probed names abort the process at the first jit, and every one of them appears in a blog post, an issue, or older release notes. The list is not worth reproducing — probe, don't trust: set the flag in a subprocess and see whether XLA dies. Four patterns cover almost all of it.

  • Renamed: --xla_gpu_asm_extra_flags → --xla_gpu_ptx_compiler_extra_flags · --xla_gpu_autotune_cache_dir → --xla_gpu_experimental_autotuner_cache_dir · --xla_gpu_enable_cuda_graphs and the whole graph family → --xla_gpu_enable_command_buffer (pass the empty string to disable; NONE is not a value) · --xla_gpu_enable_address_computation_fusion → _enable_dynamic_slice_fusion. All four of the most-cited dump flags (--xla_dump_optimized_hlo_proto_to and siblings) are gone — use --xla_dump_to + --xla_dump_hlo_as_proto.
  • Never existed as a flag: --xla_gpu_enable_priority_fusion (priority fusion is unconditional) and --xla_gpu_enable_triton_softmax_fusion (there is no flag to turn off the diamond rewriter; only --xla_disable_hlo_passes=triton-softmax-rewriter reaches it).
  • Documented upstream, absent here: six names on openxla.org/xla/flags_guidance (--xla_gpu_pipeline_all_gather, --xla_memory_scheduler, …) exist in none of this build. That page is written against a different, largely TPU, build.
  • Pass names that parse and do nothing: instruction_fusion, fusion_merger, horizontal_loop_fusion — zero occurrences in the plugin .so, yet --xla_disable_hlo_passes=<any of them> returns rc 0. See Trap 1.

Two API-level entries belong here too. jax.custom_transpose does not exist in 0.10.2 (deepwiki asserted otherwise); use jax.interpreters.ad.deflinear2. And JAX_XLA_BACKEND, JAX_CUDA_VISIBLE_DEVICES and their siblings are dead env vars — the config options work via jax.config.update, but these are *_flag declarations whose call sites never call os.getenv.

The env-var rule that tells you which JAX config options read the environment Every *_state helper (bool_state, enum_state, optional_enum_state, enum_class_state, int_state, float_state, string_or_object_state) auto-reads os.getenv(name.upper()) at import — so jax_persistent_cache_min_compile_time_secs → JAX_PERSISTENT_CACHE_MIN_COMPILE_TIME_SECS with no per-option code. The 23 *_flag options do NOT; they only get an env default if the call site passes one explicitly. That is the entire explanation for the dead env vars above.

Two corollaries. A bad env value aborts at import jax, it is not ignored (JAX_LOG_COMPILES=maybe → exit 1). And Flag-type options have no attribute access and no context manager — config_states holds 110 entries while config.values holds 133; use jax.config.values[name] or _read(name). This is also why introspecting a string_flag with getattr produces a false "ABSENT" verdict. measured here
