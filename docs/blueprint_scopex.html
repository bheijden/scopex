Profiling a jitted JAX program

Two routes. The quick one works on any jitted function from any library, unmodified. The instrumented one needs fifteen lines in a framework and answers one more question: whose code is this?

scopex 0.1.0 · jax 0.10.2 · every number below is measured and reproducible: python examples/marked_framework.py · per-instrument limits: DEFICITS.html · github.com/bheijden/scopex

§0What this answers, and in what order

A slow compile has several possible causes living in different stages, and they want opposite responses. The order below is not a suggestion — asking a later question before an earlier one produces confident, wrong answers.

questioninstrumentcost
Which STAGE — tracing, lowering, or the backend?scopex.record1 compile, no flags
Trace-bound: WHICH PYTHON FRAME, and which line of mine?scopex.tracing1 trace, no compile
Backend-bound: which PHASE — passes, emitter, LLVM, codegen?scopex.phases1 compile, dumped
Which XLA PASS?scopex.pass_timings1 compile, subprocess
Which SOURCE LINE?walk + attribute0 compiles
Is it N COPIES of one computation?scopex.sharing0 compiles
What SURVIVED to the backend?walk_hlo1 compile
WHOSE code — library or user?the same, once marked0 compiles

The two stage-refining rows are the ones that took longest to get right, because record reports each of them as a single number and every other level in this package starts at the jaxpr — which is the output of tracing and the input to the backend. Neither end was reachable until this release. §7 routes each question to a worked recipe.

why order matters Source attribution explains time spent in tracing and in HLO passes. It says nothing about time spent in kernel autotuning — that time is spent RUNNING candidate kernels, not analysing your code, so the prettiest line-level report will point at code that is not the problem.

§1The differential method: measure a control

Every view in this document is a number. On its own a number means almost nothing — "this program has 7,000 equations" is not a diagnosis, and neither is "the backend takes 13 seconds". The method that makes the views diagnostic is to measure a control: a near-identical program that compiles fast. Everything that differs between the two arms is the pathology, and nothing else is.

Where a control comes from

  • the commit before the regression
  • the same computation written differently — x[i, j] versus x_flat[i * N + j], a python loop versus scan
  • one flag flipped, one donate_argnums removed, one dtype changed
  • the same program one size smaller, if the pathology is superlinear
why it is worth the second compile A real pathology once needed a trailing jnp.sum to appear at all: the chain without the reduction compiled in 0.4 s, with it in 80 s. A minimal example written from the description alone — omitting the reduction — reproduced nothing and would have been reported as "cannot reproduce". The control is what tells you which half of your program matters.

The procedure

# 1. do the stage splits differ?
scopex.record(case, *a) ; scopex.record(control, *a)

# 2. does the pass time ACCOUNT for the backend time?
sum(scopex.pass_timings(src)["passes"].values())  # vs t["backend"]

# 3. dump BOTH, then find the pass at which they diverge
with scopex.dump(passes=".*") as d:
    jax.jit(fn).lower(*a).compile()
# count instructions per snapshot, plot count vs pass index, for both arms

# 4. structure at every level, and SHAPES not just counts
scopex.attribute(units, "kind")
scopex.attribute(units, lambda u: str(u.eqn.outvars[0].aval))

# 5. sweep the size. a signal that does not grow is not a signal.

Reading a null honestly

The diff can come back empty, and that is information rather than failure. Measured on a known pathology (chained 2-D fancy indexing on CPU, whose pathological arm compiles 37× slower than its control):

                        case   control   ratio
jaxpr equations           80        56    1.43x
optimized HLO instrs      73        70    1.04x
pass_timings total     ~0.01s    ~0.01s    1.0x

The two programs are structurally near-identical, and XLA's own per-pass timer accounts for roughly 1% of a compile that takes seconds. Three knobs return nothing — which localises the cost to somewhere the pass timer does not reach, and that is a routing result, not a dead end. What it is not is licence to pick the largest number you can find and call it the cause.

§2The quick way — any jitted function, unmodified

You have a jitted function that got slower, and you do not control the libraries it calls. The outputs below come from examples/marked_framework.py — a 24-dimensional fixed-point solve, small enough to run in a second and large enough that every view says something.

1. Which stage?

import scopex
print(scopex.record(program, x0))
stage        seconds   share
----------------------------
trace          0.144   12.1%
lower          0.515   43.2%
backend        0.527   44.2%
unaccounted    0.006    0.5%
WALL           1.192

This is the fork in the road and it costs one compile. Had trace dominated, the problem would be your Python and XLA innocent — no point reading HLO at all. Here it splits almost evenly between lowering and the backend, so both are worth looking at and neither is a runaway. The numbers come from jax.monitoring, which JAX emits itself: not sampled, not estimated.

2. Which XLA pass?

backend is ONE number covering HLO passes, autotuning and codegen. Split it:

r = scopex.pass_timings("""
import jax, sys; sys.path.insert(0, "examples")
from marked_framework import program, X0
jax.jit(program).lower(X0).compile()
""")
r["coverage"] # READ THIS FIRST. fidelity 1.0012 · coverage 2.24% · verdict ELSEWHERE
r["passes"]   # {'simplification': 0.00117, 'layout-assignment': 0.00065, ...} — 93 passes
r["n_lines"]  # 832 — if this is ~0, the log never happened
r["raw"]      # the log itself: .grep(" min "), .verify() — show your working
read coverage before passes It carries two ratios that are never merged. fidelity is scopex's pass-second sum against XLA's own (cumulative:, max:, #called:) printed on every pass line — a self-check whose correct value is ~1.000 on every program, backend and machine, measured [0.9978, 1.0015] across twenty arms. coverage is the leaf pass seconds over jax.monitoring's backend seconds from the same child process — a measurement with no correct value, measured 0.01%–99.75% across the corpus. A low coverage is a result about your compile; only fidelity, lines_lost and biggest_pass_lost ever mean the instrument failed. Branch on coverage.checked: if a future XLA stops printing its own totals, the guard goes silent rather than loud and broken stays False.
why a subprocess TF_CPP_VMODULE is read by the C++ logging layer when the shared library loads — during import jax. Measured: set before the import, 829 log lines; set after, 0. There is no in-process route, so scopex spawns one for you.

If the passes sum to a small fraction of backend, the time is below the HLO pass pipeline — the emitter, LLVM, linking — and no amount of source attribution at the pass level will help. Go to pass_timeline (§8).

on GPU, high coverage does not mean "an HLO pass was slow" XLA registers the autotuner as a pass, so kernel-running time lands inside a pass timer. convT64_dilate16 and gemm_shapes_k16 are indistinguishable here — both ~98% autotuner, both PASS-BOUND, both fidelity ~1.0 — and their causes are opposite: on the first, 49.7% of the pass is cuDNN kernels executing on real 134 MB buffers; on the second, 0.11% is kernel time and the seconds are spent compiling 456 Triton candidates. 450× apart, identical in everything pass_timings reports. from scopex.autotune import autotune_cost splits them; the ablation --xla_gpu_autotune_level=0 confirms it (52.22 s → 0.309 s, 169×).

4. What survived to the backend?

opt = list(scopex.walk_hlo(jax.jit(program).lower(x0).compile()))
scopex.attribute(opt, "site")

250 jaxpr equations become 597 optimized instructions, and the shares MOVE:

              jaxpr        hlo_opt
user          46.0%   ->    19.6%
library       54.0%   ->    46.9%
<unmarked>     0.0%   ->    33.5%

A third of the shipped module belongs to no line anyone wrote — XLA's own bookkeeping. Reading the jaxpr split as "what the backend spends its time on" would have been wrong by more than a factor of two on the user's share.

source lines exist below the jaxpr, indirected It is tempting to read a metadata dict of {op_name="..."} and conclude the optimized module carries no source location. It does: jaxlib emits stack_frame_id=N indexing module-level FileNames/FunctionNames/FileLocations/StackFrames tables, and every frame has a parent_frame_id. walk_hlo follows the indirection and applies the same jax-tree filter source_info_util.user_frames applies at the jaxpr level — which is exactly why the two levels join on site.

What this route cannot give you: whose code it is. Every line above is yours or a library's, undifferentiated, because nothing has told scopex where the boundary is.

§3The instrumented way — a framework maintainer

You maintain mylib. Users subclass Block and implement forward and residual. When they report a slow compile you cannot tell whether it is your engine or their model.

The whole integration

@scopex.mark_framework("mylib", ("forward", "residual"))
class Block:
    ...

Or with no scopex dependency at all — the contract is a naming convention, so your library keeps depending on jax alone:

class Block:
    def __init_subclass__(cls, **kw):
        super().__init_subclass__(**kw)                  # a REAL super() — see §3
        if cls.__module__.split(".")[0] != "mylib":      # FOREIGN subclass = a user's
            for name in ("forward", "residual"):
                fn = cls.__dict__.get(name)
                if fn is None: continue
                def wrap(fn=fn, tag=f"mylib:user.{cls.__qualname__}.{name}"):
                    def marked(*a, **k):
                        with jax.named_scope(tag): return fn(*a, **k)
                    return marked
                setattr(cls, name, wrap())

Users change nothing. They subclass Block as always.

What it buys

scopex.attribute(units, "split")
split       count    share
--------------------------
library       135    54.0%
user          115    46.0%

46% of this program is the user's model, not the engine. That is the sentence you could not say before, and it reframes the conversation. (On a larger real program the same view read 81% user / 19% library — the ratio is a property of the program, not of the tool.)

Then, where inside the engine — by="library" keeps the full nesting:

mylib subsystem         count    share
--------------------------------------
solve/step                135    54.0%
solve/step/assemble       111    44.4%
solve                       4     1.6%

And the one only instrumentation reaches — the interaction:

scopex.crosstab(units, rows="library", cols="transform")
# solve/step/assemble  ×  vmap/transpose/jvp  =  51
# solve/step           ×  transpose           =   6

51 equations compiled under transpose — the reverse-mode adjoint — in a program that only called solve. That is assemble running jacrev over the user's residual to build its operator. Nothing in the user's code asked for reverse mode; the library's own construction put it there, and the crosstab is what makes that visible.

full sequences, never a first match by="author" keys on the WHOLE nesting, so a hook reached through another hook is its own bucket rather than being merged into either. On one real program the nested and the direct populations were 3,373 and 1,168 equations — different questions with different answers. An accessor that returned only the innermost once collapsed 4,567 equations into a reported 1,168. Every accessor here returns the full ordered sequence for that reason; by="innermost_author" is the explicit opt-in.

§4The naming contract

<pkg>:<role>[.<detail>]        role ∈ {lib, user}

"mylib:lib.assemble"              # engine internals
"mylib:user.MyModel.residual"  # a user's hook implementation

A convention, not an API — which is the point. Were it an API, every framework adopting it would take a runtime dependency on a profiler and the two would be version-locked forever. pkg namespaces the mark, so two marked frameworks in one program do not collide: marks nest and none is overwritten.

never put / in a scope name jax renders a name stack by joining entries with /. Measured: two nested scopes "a" then "b" and one scope named "a/b" BOTH render to 'a/b'. At the jaxpr level name_stack.stack still distinguishes them; below the jaxpr only the rendered string survives, so the / is unrecoverable. Use . inside names. Everything else measured safe verbatim to optimized HLO: : . - _ spaces, brackets, parens, mixed case, digits, non-ASCII.
a real super() The hook must use the zero-argument super() inside a class body, or super(base, cls) closing over the DEFINING class. Writing super(cls, cls).__init_subclass__ — where cls is the subclass being created — resolves straight back into the wrapper and recurses until the stack blows. Measured, in all three shapes tried.

Cost: not measurable. 21 order-rotated rounds paired within round: one scope per leaf 1.029×, two nested 1.007×, per-round range 0.485–1.157 — the effect is below this measurement's noise. Building the representation costs 1.7 µs/equation unmarked, 3.5 µs marked.

Limit: the subclass hook reaches frameworks whose extension point IS subclassing. A library of plain functions has nothing to hook, and the failure is not silence but a wrong answer — an unmarked user callable ingested by a framework reports as library-authored. Use scopex.mark_callable(fn, "mylib", "vector_field") at the point of ingestion.

The split is binary. Ecosystem middleware (a flaxformer module under flax) is foreign, so it reads as user-authored. scopex warns the first time a framework marks subclasses from more than one package root; when that fires, use by="author" or by="file", which keep the roots apart.

Every accessor scopex ships exists because the obvious call returns a plausible, empty answer. Counting occurrences of a scope that is demonstrably present:

The compiler_ir rows are the dangerous ones: it is the accessor that looks structured, so its empty answer gets believed. Use scopex.stablehlo_text() and scopex.hlo_text() — or, better, scopex.stablehlo_module(), which hands you the ir.Module itself with nothing re-lowered.

a correction, and it cost this package a whole parser This table used to read "compiler_ir('stablehlo') — drops locations", and that explanation is false. The count of 0 is real, but it is Operation.__str__'s enable_debug_info=False default, not the IR. The same object printed with enable_debug_info=True is byte-identical to as_text(debug_info=True) — verified again for this release: 958 chars, 20 loc(, and compiler_ir('stablehlo') is compiler_ir('stablehlo'), so nothing is re-lowered and nothing is copied. The trap is real; the conclusion drawn from it — "this route cannot see provenance" — was not, and it is precisely why walk_stablehlo was originally written as a line parser over printed text. That parser then returned 1 unit on 16 of 21 real programs. A wrong explanation for a real observation is worth more scrutiny than the observation.

Enabling the heavy instruments

before import jaxafter import, before 1st compileafter 1st compile
XLA_FLAGS=--xla_dump_to30 files30 files0 — silent
TF_CPP_VMODULE829 lines0 — silent0

That asymmetry is the whole API. Dumping can be switched on in-process, so scopex.dump() is a context manager that RAISES when the backend is already up — an empty dump directory reads as "nothing to see" rather than "you asked too late". vmodule cannot be, so pass_timings spawns a subprocess. TF_CPP_VMODULE alone does nothing regardless: importing jax sets TF_CPP_MIN_LOG_LEVEL=1, suppressing every VLOG.

the fusion decision log is GPU-only priority_fusion_dump.txt appears on GPU (77 dump files) and not on CPU (27). Its absence is not evidence that no fusion happened. And more generally: the device decides which passes run at all — one known pathology measures 248× on CPU and completely flat on GPU. Never report "no effect" without naming the backend.

why some of these are scopex.module.name The package exports 50 names. Everything else is reachable but not top-level, because it was asked for by one or two of the thirty investigations rather than used constantly — backend_split, trace_profile, jaxpr_sharing, emitter_growth, fusion_steps. Each is a worked recipe in examples/recipes/, which shows the whole procedure instead of hiding it behind a name. Promote one when three unrelated recipes reach for it.

Run verify_parity on your own program; disagreement is a scopex bug.

§7Recipes — one file per question

The recipe overview groups all twenty by the question you arrived with and links each to the pathology it was written against. The routing table below is the same set, keyed on what your stage split said.

examples/recipes/ holds a runnable module per question. Each one names the corpus case it was derived on, prints the numbers it was derived from, and documents the conditions under which its knob stops working. They are not demos: every number in every docstring was measured, and where a re-run disagreed with the original the recipe says so and keeps both.

start here trust_the_instrument.py first, in a fresh process, then stage_split.py. The first asks whether the levels are reading your program at all; the second decides which of the rows below you are in. Everything else is downstream of that answer.

read the caveat, not just the number Two live traps the recipes carry because they were hit while writing them. §8Reading a dump

Most of what XLA knows about your compile is already on disk the moment you ask for it. A dump is the only route to the per-pass module snapshots, the emitter's own MLIR, the LLVM IR, the object file, the fusion decision log — and to the timestamps, which are the only in-package instrument that reaches phases XLA does not time.

the trap that makes a dump silently empty XLA reads XLA_FLAGS when its backend is first initialised. Setting it after any compile — or after anything that commits an array to a device, including jnp.ones(1) at module scope — is a silent no-op, and you get an empty directory and conclude there was nothing to see. scopex.dump and scopex.phases both raise rather than allow it. Two arms means two processes.
what a dump costs, and it is unwarned dump(passes='.*') on one corpus arm produced 944 MB across 950 files in 358 s — from a 24-equation jaxpr. Another produced 1,089 files. Dumping also perturbs what it measures: writing snapshots costs wall time that lands in the pass-pipeline bucket (+5.8% on one case, +36% on a 729-file one), so shares from a dumped compile are internally consistent but their absolute seconds must not be compared against an undumped record().

The timestamps are an instrument — and it is now a checked one

why you can believe the tail Every glog line carries a CLOCK_REALTIME microsecond timestamp, and st_mtime is on the same clock. XLA writes each snapshot inside the pass's scoped timer, so mtime(after_P) must fall between that pass's START and END log lines — a falsifiable test of the alignment itself, not of a number derived from it. Measured: 683/683 snapshots inside their own pass timer, 100.0%, across 12 compiles and 5 programs including a 4.7×-overloaded machine. scopex.timeline_agreement(src) runs one subprocess with both clocks on and returns the checked timeline; plain scopex.pass_timeline(d) with no log returns the same intervals with .verdict reading UNVALIDATED, which is what it always was and now says so. The tail carries an error bound (worst observed mtime-vs-µs offset, 0.11–0.18 ms) and an SNR, not an adjective — and its emitter/LLVM/codegen split is suppressed when 223 kernel modules compile concurrently, because those boundaries then order nothing.

XLA writes each snapshot as its pass completes, so consecutive mtimes bound the pass between them — and the interval between the last HLO snapshot and the first .ll is everything XLA's pass timer cannot see. On jax#32704 (chained 2-D fancy indexing, CPU) that is the entire finding: the HLO pass pipeline accounts for 0.1% of the compile and <llvm ir emission> for 99.5%, while every count-based view is a null — jaxpr equations identical, optimized instructions 1.04×, emitted IR +16 lines.

from scopex.phases import backend_split
backend_split(fn, x)         # hlo_passes 0.15% · emitter 99.12% · llvm_opt 0.29% · codegen 0.18%
                             # sound=True · coverage 0.997 · 1 kernel module
why sound and coverage come first XLA:CPU compiles kernel modules concurrently, so global phase boundaries only describe a real ordering when there is exactly one. On a 223-kernel program the phases interleave 223/223 and per-kernel intervals sum to more than the backend stage they sit inside — so backend_split reports one below_hlo bucket and sound=False rather than inventing a split. That matters because multi-kernel is exactly where LLVM and codegen are the answer: a splitter that quietly mislabelled there would have its blind spot aligned with the quantity it measures. Note the interleave test is not redundant with coverage — that program's coverage was 0.924, comfortably inside any reasonable band.
no .ll and no .o is a result, not a failure A program that constant-folds to a literal emits no LLVM module. So does one XLA hands to a library kernel: jnp.tanh(x).sum() dumps 26 files and not one LLVM artifact, because the optimized module is a single kind=kCustom fusion with backend_config {"kind":"__ynn_fusion"}. There is then nothing timestamped to measure to, and backend_split says so (coverage 0.196, sound=False) instead of reporting a measured zero.

§9What it will not tell you

It does not rank lines by compile seconds. It attributes STRUCTURE — equations, instructions, fusion decisions. Time attribution below the stage split needs per-pass timing, and even that does not divide cleanly by source line.

correct is not the same as actionable On a known scatter pathology all eight scatters attribute to ONE source line, and per-instruction interventions on that line span a 19.6× range in effect. The line is 100% correct and 0% sufficient. Attribution locates; it does not decide.

It will not find your pathology for you. It builds the map. Interventions tried against it — barrier placement, region bisection — declined on every real program tested.

Counts do not scale with problem size. vmap batches rather than unrolls, so a program at N=8 and N=30 gives byte-identical equation counts. Reading a count as "cost per stage" is wrong.

Nested-jit trace time is invisible to the stage split. JAX emits the tracing timer only when core.trace_state_clean() (jax/_src/pjit.py:528), so tracing inside an inner jit is folded into the parent and cannot be separated by record. scopex.tracing hooks CPython frames rather than pjit and does separate it — on a nested-jit fib it charges 44.2% to the user's own fib, across 22 nested _trace_for_jit calls.

the same guard, failing silently — worth knowing That guard has a worse consequence than a missing breakdown. A top-level vmap or grad over a jitted callee pushes a trace, so no enclosing jit event exists and the trace metric reads a silent 0.0. Measured with a 10-operand einsum(optimize='optimal'): jax.jit(inner).lower(*xs) reads wall 2.518 s / trace 2.511 s, but jax.vmap(inner)(*xs) reads wall 2.711 s / trace 0.001 s — 2.651 s missing, landing in unaccounted, whose docstring used to blame dispatch or host transfer. Timings.matched stays True throughout, so nothing warned. record() itself is safe (it always wraps in jax.jit(fn).lower(...)); timing your own jax.vmap(jitted)(...) with a listener is not. Timings.trace_looks_blind now flags exactly that combination.
