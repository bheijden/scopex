The pipeline

What each stage of JAX → StableHLO → HLO → PTX actually does, what it costs, which instrument can see it, and where the GPU and CPU backends diverge. This is the map scopex instruments; every stage below names the call that observes it.

Measured on jax / jaxlib 0.10.2, jax[cuda13], sm_89, CUDA 13.0, 20 cores. "Compile time" is not one thing — it decomposes differently on different programs, and if you do not know which box below owns your seconds, no flag can help you.

1.1 · Eager problem construction — the biggest single line item

What happens. Every jnp operation executed outside a jit goes through dispatch.apply_primitive → dispatch.xla_primitive_callable, which is literally api.jit(prim_fun), memoised per (primitive, params). So each distinct (primitive, shape, dtype) your construction code touches eagerly costs one full trace + lower + XLA compile of a one-instruction module.

What knob exists. None in the compiler. The fix is to keep problem construction off the device — host arithmetic in numpy/math, or wrap the whole construction in one jax.jit. The second-order fix is jax_persistent_cache_min_compile_time_secs = 0: at the default of 1.0 s these sub-second modules are never written to the persistent cache and are re-paid on every process start, forever, while the cache directory still fills with autotune textprotos so it looks like it is working.

1.2 · Tracing — Python runs, the jaxpr grows

What happens. Primitive.bind reads trace_ctx.trace; inside a jit that is the DynamicJaxprTrace, whose process_primitive appends an equation. Your Python body executes exactly once per trace. Roughly 2.3 binds per emitted equation on real code (solver B 7,537 binds → 3,292 equations; solver D 7,648 → 3,278) — the excess is transform layers (batching, AD) that bind and forward.

What it costs. 7–15% of a cold run. Linear in emitted equations: a synthetic sweep from 1,280 to 20,480 equations gives a local exponent of 1.04 at 98–109 µs/equation. Real code costs 3.4–7× more Python per equation:

A least-squares fit on three models gives T = 0.192 s + 348.5 µs·n; held out it errs +35.4% / +8.6% / −43.1%. The killer pair is in the table: solver D 3,278 equations → 2.345 s against solver B 3,292 equations → 1.291 s, 1.82× apart at a 0.4% difference in equation count. core.bind call count fails identically (7,537 vs 7,648 binds, 1.81× the time).

What you can see. cProfile is the instrument that explains the 1.82×, and the jaxpr is not: 78% of trace self-time is in jax/_src in both programs and the model's own code is 0.6%. The difference lives in which internals — solver D spends 2.148 s cumulative in batching.process_primitive and 1.484 s in pjit._pjit_batcher (vmap layers re-tracing inner pjits); solver B spends 0.834 s in core.eval_jaxpr (inlining). Same equation count is not the same amount of Python. Note cProfile inflates tracing by a constant 1.68× on this box (measured on two programs independently) — ratios survive, absolute seconds do not.

The three caches in front of tracing, and which one costs what

Read in this order. Only the third re-runs your Python.

  1. C++ PjitFunction cache (pjit.py:248-292). Key is JitGlobalCppCacheKeys plus the per-call argument signature. A hit never enters Python. Global when the jit declares no explicit attributes.
  2. pjit._infer_params_cached (pjit.py:594), a weakref_lru_cache. PjitInfo.__hash__ = id(self) and __eq__ is identity, so a freshly built jax.jit(f) wrapper always misses this one.
  3. pe.trace_to_jaxpr (partial_eval.py:2268), keyed on (fun, in_avals, debug_info, qdd-context) + config.trace_context(). Missing this is the only thing that re-runs your Python.

The distinction is measurable and enormous. 25 timed calls of an 8-deep chain on f64[1024]:

Rolled tracing is flat in K (6.2–16.8 ms over a 128× range) because the body is traced once and the trip count is a parameter. At K=2048 that is 117× on trace and 21.8× on lower. lax.scan(..., unroll=k) is free at trace time (recursive equations stay at 6 for every unroll from 1 to 256) and costs 2.08× on lowering at unroll=256 — so it buys runtime without touching the trace budget.

1.3 · The jaxpr — and why it does not price anything

On all six real models, jax.jit(probe).trace(gs).jaxpr has exactly ONE top-level equation (a custom_jvp_call). Everything is in eqn.params. Sub-jaxprs live under different keys per primitive: pjit/scan under params['jaxpr']; while under ['cond_jaxpr']/['body_jaxpr']; cond under ['branches'] (a tuple); remat under params['jaxpr'] as a bare Jaxpr, not a ClosedJaxpr; custom_jvp/vjp_call under ['call_jaxpr'] — primal only, because the rules are un-traced lu.WrappedFun thunks. Trace jax.grad(f) if you want them.

Do not write a walker. jax._src.jaxpr_util already ships count_eqns, primitives, primitives_by_shape, primitives_by_source, source_locations, jaxpr_to_html, pprof_equation_profile. Verified: count_eqns(j, revisit_inner_jaxprs=True) returns exactly 7,773 on solver A, agreeing with an independent walker to the equation. revisit=False gives 6,861 — 912 equations (12%) come from sub-jaxprs reached more than once. Pick deliberately.

1.4 · Lowering — small, sub-linear, and impossible to cache away

What happens. jaxpr → StableHLO MLIR. Four corrections to the received cache story, all measured here

1.8 · Fusion and emitter selection — where the seconds actually are

The algorithm. priority-fusion runs once per module and builds a fresh PriorityFusionQueue per fusible computation. Post-order walk sets priorities; priority = time_unfused − time_fused from CombinedGpuPerformanceModel::EstimateRunTimes. A bit-width-preserving bitcast gets +inf (fused first), a constant gets −inf (fused last in an unfueled epilogue), and anything computing to a negative priority is erased from the queue, not re-inserted. Pop the max, fuse the producer into every consumer, then re-cost the grown fusion and all of its operands — invalidating four caches and re-running the cost model on each.

The cost is (candidates) × (cost-model work per candidate), and BOTH factors were measured on this box in the same session at 8,300× different per-merge cost. That is why no static graph quantity predicts it.

Emitters — XLA picks on SHAPE, and the HLO label lies

Two functions decide "emitter" and only one matters. PriorityFusion::ChooseKind writes the kind= you see in optimized HLO, mapping kTriton, kCustomFusion, kCuDnn, kSort → kCustom and kConcatenate, kReduction, kTranspose, kScatter → kInput. Its own source comment: "This shouldn't matter but some passes downstream still query these instead of fusion analysis." So kInput does NOT mean "reduction" and kCustom does NOT mean "Triton". The one that runs at codegen is HloFusionAnalysis::GetEmitterFusionKind, on the FINAL fusion, checking backend_config first, then a real reduction hero, then a tiled transpose hero, then more than one root → kLoop (this beats scatter/sort/concat), then scatter/sort/concatenate, else kLoop.

The shape rules underneath (warp = 32 here): a row reduction gets the reduction emitter iff R ≥ 32 or 32 % R == 0, i.e. R ∈ {1,2,4,8,16,32,…} — R = 12 falls off the cliff. A column reduction gets it unless major < 32, or major < 64 and minor < 32, or major < 128 and minor < 8, or major < 256 and minor < 3. A tiled transpose needs both swapped dims ≥ 16, or both ≥ 8 with product ≥ 8192.

Correction: the rank pathology is the Triton path, not CoalescingAnalysis indexing maps A prior report attributed the rank pathology to GpuPerformanceModel::EstimateRunTimeForFusion → CoalescingAnalysis::Create → ComputeThreadIdToInputIndexing, "an IndexingMap whose DimVar count is the rank". The heuristic is opcode pattern-matching. The maintainers' own cost-model discussion (openxla/xla #10065) says the same: read coalescing uses heuristic pattern matching, and indexing analysis is still being developed.

1.10 · Load and launch — and the cache that is not yours

cuModuleLoadFatBinary receives a pure sm_89 cubin — cuobjdump -ptx on it returns nothing. There is no PTX for the driver to JIT, so the CUDA driver's PTX→SASS cache (~/.nv/ComputeCache) is never touched by an XLA compile. Five independent confirmations, including a positive control: a warp-lang module load in the identical setup produced 3 files / 230,010 B where JAX produced 0, so the zeros are a real negative and not a silently-ignored env var.

Therefore CUDA_CACHE_DISABLE=1 is a no-op for a JAX compile benchmark — there is no warm-cache confound to remove. The 334× cold/warm effect this project measured belongs to Warp/NVRTC, which hands the driver PTX (§7, Mode G). The shared cache stays a live hazard for mixed jax+warp benchmarks: it sits here at 1,648 files / 1.07 GB, on its cap and evicting.

What is architecturally different

  • No priority-fusion. Zero occurrences in any CPU pass log. CPU runs a pass literally named fusion = CpuInstructionFusion, a classic InstructionFusion subclass with no cost-model re-costing — none of the O(merges) × O(re-cost) loop. Its limits are hard constants, and one exists explicitly to bound compile time: kMaxReductionsInFusion = 5, with the source comment "Fusing too many reductions together can lead to a giant LLVM modules after loop unrolling… to avoid excessive compilation times." The CPU backend does automatically what the GPU blueprint tells you to do by hand.
  • No autotuner. Three checks agree: no LlvmKernelAutotuner/CpuCodegenBackend/CpuProfiler symbol in libjax_common.so; no pass named autotuner in any CPU pass log (against 226 invocations and 4.12 s on GPU for the same program); and --xla_gpu_autotune_level=0 parses on CPU and is a measured no-op. The autotune-bound regime cannot exist on CPU.
  • 189 GPU passes vs 93 CPU passes, 72 shared. GPU-only (so disabling them on CPU is a provable no-op): autotuner, priority-fusion, cublas-gemm-rewriter, multi_output_fusion, remat-pipeline, triton-softmax-rewriter, layout_normalization, … CPU-only: fusion, post_scatter_expansion_simplification, while-loop-invariant-code-motion, cpu-parallel-task-assigner, gemv-rewriter, dot-library-rewriter, triangular_solve_expander, conditional-to-select, …
  • There is no single pass to attack on CPU. The biggest is fusion at 22.8% of the pass half, which is itself ~40% of compile — so the best possible pass-level win is ~9%. (GPU, same program: priority-fusion 64.6%.)
Refuted: "StableHLO is backend-independent, so the pre-backend half is shared" False for any JAX program containing linear algebra, and the divergence starts one stage earlier than everyone assumes. The one genuinely new CPU recommendation. If your program is dot-heavy (MLP / transformer / anything the GPU autotunes), JAX_PLATFORMS=cpu compiles it ~60× faster — synthetic dot-8: 61 optimized instructions and 24 custom-calls at 6.58 s on GPU against 35 instructions, 0 custom-calls, 0.11 s on CPU (0.016×, measured twice).
